# Quality Checklist

Quality checks to verify before writing any ArcKit artifact to file.
Run all **Common Checks** plus the relevant **Per-Type Checks** section for the artifact being generated.
Fix any failures before proceeding to write.

## Common Checks

All artifacts must pass these 10 checks:

1. **Document Control complete** -- All 14 standard fields populated (Document ID, Document Type, Project, Classification, Status, Version, Created Date, Last Modified, Review Cycle, Next Review Date, Owner, Reviewed By, Approved By, Distribution).
2. **Document ID convention** -- Follows `ARC-{PROJECT_ID}-{TYPE}-v{VERSION}` pattern (e.g., `ARC-001-REQ-v1.0`). Multi-instance types include a sequence number (e.g., `ARC-001-ADR-001-v1.0`).
3. **No placeholder text** -- No remaining `[PLACEHOLDER]`, `TODO`, `TBD`, `XXX`, or `YYYY-MM-DD` tokens. All fields contain real values.
4. **Classification set** -- One of: PUBLIC, OFFICIAL, OFFICIAL-SENSITIVE, SECRET.
5. **Status set** -- One of: DRAFT, IN_REVIEW, APPROVED, PUBLISHED, SUPERSEDED, ARCHIVED.
6. **Revision History present** -- Table with columns: Version, Date, Author, Changes, Approved By, Approval Date. At least one row for the initial version.
7. **Generation footer present** -- Standard footer at end of document with Generated by, Generated on, ArcKit Version, Project, and Model fields.
8. **Clean Markdown** -- No broken tables, unclosed code blocks, malformed links, or rendering issues.
9. **Consistent tables** -- All tables have header separators, aligned columns, and no missing cells.
10. **Proper heading hierarchy** -- No skipped heading levels (e.g., jumping from `##` to `####`). Logical document structure maintained.

## Per-Type Checks

### OAAL — O-AA ADM Lite

- Sprint-to-ADM mapping present for all 8 phases (Preliminary through H)

- Engagement window defined (2–4 weeks with sprint breakdown)

- Architecture vision output from Sprint 1 documented

- Backlog-driven approach with user stories per ADM phase

- Traceability to O-AA C208 axioms (especially Axiom 11: Agile Architecture)

- Sprint review outputs documented (architecture artefacts per sprint)

- Stakeholder engagement cadence defined per sprint cycle

### OAPR — Agile Product Architecture

- Product mission statement and outcome definition present

- Cross-functional team structure documented (roles, responsibilities)

- Backlog items mapped to architecture components

- Product-centric view vs system-centric view clearly distinguished

- Value stream mapping included if multi-product portfolio

- Traceability to O-AA C208 Chapter 12 (Product Architecture)

### OASTR — Agile Strategy

- Dual transformation canvas present (legacy modernization track + greenfield innovation track)

- Strategy options documented with decision criteria

- Agile roadmap with time-boxed milestones

- Business outcome metrics defined per strategic initiative

- Traceability to O-AA C208 Chapter 10 (Strategy)

- Portfolio alignment with investment decisions documented

### OASEC — Agile Security

- Security backlog items integrated into sprint planning

- Threat modeling outputs per sprint documented

- Compliance evidence collection mapped to sprint deliverables

- Security controls assessed in continuous (not gate-based) model

- Traceability to O-AA C208 Chapter 17 (Security)

- Residual security risk documented after sprint mitigations

### OAGOV — Agile Governance

- Governance cadence aligned to sprint cycle (not quarterly boards)

- Architecture review gates defined per sprint or release

- Lightweight compliance evidence collection approach

- Change management process operating at sprint velocity

- Traceability to O-AA C208 Chapter 18 (Governance)

- Governance artefacts minimal (no more than 2 per sprint)
