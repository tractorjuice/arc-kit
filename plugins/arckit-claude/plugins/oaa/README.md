# ArcKit — Open Agile Architecture (O-AA) Overlay

5 slash commands and the `oaa-full` build recipe for agile enterprise architecture
using Open Agile Architecture (C208) — product-driven, sprint-based delivery:

| Command | Doc Type | Description |
|---------|----------|-------------|
| `/arckit-oaa:oaa-adm-lite` | `OAAL` | Maps TOGAF ADM cycle to agile sprints (4–8 week engagement windows) |
| `/arckit-oaa:product-architecture` | `OAPR` | Product-centric architecture — cross-functional teams, backlog-driven delivery |
| `/arckit-oaa:agile-strategy` | `OASTR` | Dual transformation canvas — digital transformation + agile transformation |
| `/arckit-oaa:agile-security` | `OASEC` | Security embedded in sprint rhythm — threat modeling, compliance evidence |
| `/arckit-oaa:agile-governance` | `OAGOV` | Lightweight governance cadence aligned to sprint cycles |

Recipe: `oaa-full` — all five O-AA commands (ADM Lite → product → strategy → security → governance) on top of the core `PRIN`/`STKE`/`REQ` foundation.

**Official standard:** <https://publications.opengroup.org/c208> (full text behind Open Group sign-in)

## Requires arckit core plugin

```bash
claude plugin install arckit arckit-oaa
```

On Claude Code v2.1.143+, `claude plugin disable arckit` will refuse with a copy-pasteable disable-chain hint while `arckit-oaa` is enabled. Without `arckit` (core), the recipe will not resolve foundation commands (`arckit:principles`, `arckit:requirements`, etc.) and `validate-arc-filename` will not recognise O-AA doc-type codes (`OAAL`, `OAPR`, `OASTR`, `OASEC`, `OAGOV`).

## Configuration (userConfig)

The overlay's templates substitute `${user_config.*}` placeholders at render time so no organisation-specific identifiers are hard-coded. Keys are declared in `.claude-plugin/plugin.json` and prompted for when you enable the plugin. Effective values are read only from **user settings** (`~/.claude/settings.json` → `pluginConfigs`), `--settings`, or managed settings — a `pluginConfigs` block committed to a repo's `.claude/settings.json` is ignored (Claude Code v2.1.207+).

| Key | Default | Effect |
|-----|---------|--------|
| `organisation_name` | empty → `[PENDING — organisation]` | Organisation/client name in doc-control headers and sample YAML |
| `project_issue_prefix` | `ARC` | Identifier prefix for engagement/parent issue references (e.g. `ACME-128`) |
| `safety_checklist_id` | empty → `[PENDING — safety checklist ID]` | Checklist ID referenced in `governance-report.yaml` |
| `references_dir` | empty → organisation-specific references omitted | Directory of external reference docs (ADRs, study notes); rendered lists use relative paths only |

```json
// ~/.claude/settings.json
{
  "pluginConfigs": {
    "arckit-oaa": {
      "organisation_name": "Acme Corp",
      "project_issue_prefix": "ACME",
      "safety_checklist_id": "ACME-SAFETY-001",
      "references_dir": "~/docs/acme-arcade-refs"
    }
  }
}
```

Notes:

- Substitution happens at render time per `templates/_partials/RENDERING.md` — each command's prompt instructs the model to apply these rules when reading the template.
- The doc-control partial has a code path too: `scripts/python/apply_doc_control_marker.py`.
- Non-Claude targets (Codex/Gemini/etc.) generated by `scripts/converter.py` receive plain `${KEY}` placeholders and rely on the defaults above — `user_config` substitution is Claude-only.
- `scripts/check_references.py` validates that every `${user_config.<KEY>}` in a template is declared in a `userConfig` block.

## Scope

**In scope (v1)**: C208 content — Part 1 O-AA Core (Ch. 3–9, including the 16 axioms of Ch. 9), Ch. 11 Agile Strategy, Ch. 14 Product Architecture, Security by Design (Ch. 4.6 / Axiom 16 / G216), Ch. 8 Agile Governance. Sprint-driven engagements for rapid architecture delivery.

**Out of scope**: Full TOGAF ADM (deferred to `arckit-togaf-adm` overlay), traditional stage-gate architecture processes. Each O-AA command is designed to run in 2–4 week sprint windows.

## How It Works

Each command is a **prompt template** — not an interactive questionnaire. The AI reads your project context and existing artifacts, then fills the template sections. No step-by-step prompts; it's all context-driven generation.

### Dependency Chain

```text
PRIN → STKE → REQ → OAAL → OAPR → OASTR → OASEC → OAGOV
```

Foundation commands (`principles`, `stakeholders`, `requirements`) should run first; each O-AA command reads them when present and notes the gap when they are missing. The O-AA order follows what each command reads: product architecture reads the ADM Lite sprint plan, the strategy canvas reads both, and security and governance read all three. Breaking core `arckit` (=6.18.3) breaks doc-type validators.

### Artefact Naming

Output uses the `ARC-NNN-TYPE-vN.N.md` convention:

| Artefact | Example filename |
|----------|-----------------|
| O-AA ADM Lite | `ARC-001-OAAL-v1.0.md` |
| Product Architecture | `ARC-001-OAPR-v1.0.md` |
| Agile Strategy | `ARC-001-OASTR-v1.0.md` |
| Agile Security | `ARC-001-OASEC-v1.0.md` |
| Agile Governance | `ARC-001-OAGOV-v1.0.md` |

### Handoff Behaviour

Commands declare explicit next-step targets. Claude Code auto-suggests subsequent commands mid-engagement:

```text
/arckit-oaa:oaa-adm-lite "my project"
  → Handoff: product-architecture ("Design product-centric architecture")
  → Handoff: agile-strategy ("Plan dual transformation")
  → Handoff: agile-security ("Embed security into sprint rhythm")
  → Handoff: agile-governance ("Establish governance cadence")
```

## What Each Phase Produces

### `oaa-adm-lite` — Sprint Map

| Section | Fields determined |
|---------|-------------------|
| **Sprint 0 (Vision)** | AI workload type, data classification, jurisdiction, user count, latency targets, budget, constraints, stakeholder concerns, regulatory controls, high-level capabilities in scope (TOGAF Phase A) |
| **Sprint 1 (Business + Data)** | Baseline and target business capability map with gaps (TOGAF Phase B), value streams with SLAs, data asset inventory (classification, volume, encryption), data flows with compliance controls |
| **Sprint 2 (Technology)** | Model serving, vector store, database, runtime standards; GPU cluster sizing; network topology; monitoring stack; compliance validation against jurisdiction |
| **Sprint 3 (Transition)** | Migration waves, strangle pattern vs big-bang, dependency sequencing, rollback criteria |
| **Sprint 4+ (Governance)** | Ongoing review gates, change velocity thresholds, compliance evidence per sprint |

Gate criteria at each sprint: artefact matches the inlined template structure, stakeholder sign-off, regulatory baseline identified, handoff documented.

### `product-architecture` — Product & Team Ownership

| Section | Fields determined |
|---------|-------------------|
| **Mission** | One-sentence product purpose and target value |
| **Outcomes** | Value KPI, adoption target, NPS, measurable business outcome |
| **Team composition** | Product Owner, Architect, Lead Engineer, AI Safety Engineer, DevOps, QA — names, responsibilities, cadence |
| **Backlog items** | Architecture items as first-class backlog entries: story points, risk, acceptance criteria, compliance mapping |
| **Value stream** | Lead time waste, automation targets, flow from idea to production |

### `agile-strategy` — Dual Transformation Canvas

| Section | Fields determined |
|---------|-------------------|
| **Technology transformation** | Current → target technology stack, migration approach (strangler/dual-run), legacy modernization, enabling technologies |
| **Product transformation** | Project-based → permanent product teams, measurable outcomes per team |
| **Operating model** | Functional silos → platform + stream-aligned teams, capability gaps, internal platform strategy, funding model |
| **Organizational, cultural and team agility** | Decision rights, cultural change initiatives, team topology and flow metrics |
| **Resilience targets** | Business continuity, disaster recovery, fallback strategies |
| **Waves and backlog** | Transformation waves with outcome measures; strategy epics mapped to the product backlog |

### `agile-security` — Security Per Sprint

| Section | Fields determined |
|---------|-------------------|
| **Security stories** | Risk category per backlog item (data exfiltration, model poisoning, prompt injection, unauthorized access, availability) |
| **Risk-based testing** | Scan frequency by risk level: critical = every commit, high = every PR, medium = sprint gate, low = weekly |
| **Compliance-as-code** | Regulatory controls expressed as executable validation rules |
| **Threat model** | STRIDE-structured threat model, updated every sprint, not one-time |
| **Exceptions** | Sign-off by severity for a failing check, accepted risk with a resolution deadline |
| **AI bias assessment** | Algorithmic transparency checks per sprint |

### `agile-governance` — Sprint Governance

| Section | Fields determined |
|---------|-------------------|
| **Sprint review panel** | 3–5 members from the product team (Product Owner, Lead Architect, AI Safety Engineer, DevOps Lead, Compliance Representative), decision authority matrix, escalation tiers |
| **Sprint checklist** | Pre-sprint: architecture constraint check, compliance impact scan, model change review. Mid-sprint: pipeline health, in-flight decisions. Post-sprint: drift check, compliance verification, debt logging |
| **Architecture debt** | Compliance debt, scalability debt, security debt, observability debt, documentation debt — severity, introduced sprint, resolution target |
| **Quarterly health** | Architecture health score (compliance %, drift score, debt age, test coverage, documentation freshness) |
| **Change management** | `change-request.yaml` evaluated and decided by the panel within the sprint, not by quarterly boards |

## Execution Modes

### Claude Code (Plugin)

```bash
# Install
claude plugin install arckit arckit-oaa

# Run individual commands
/arckit-oaa:oaa-adm-lite "my project"
/arckit-oaa:product-architecture "Observability Stack"
/arckit-oaa:agile-strategy "enterprise AI transformation"
/arckit-oaa:agile-security "AI platform"
/arckit-oaa:agile-governance "enterprise AI platform"
```

### Codex (Skills)

```bash
# Initialize project
arckit init my-project --ai codex
cd my-project

# Skills auto-generated by converter into .codex/skills/
$arckit-oaa-adm-lite "my project"
```

### BYO LLM (CLI + Local Model)

```bash
# Configure your local LLM endpoint
arckit local setup

# Run the full O-AA recipe pipeline
arckit build --recipe oaa-full .

# Dry run (plan only)
arckit build --recipe oaa-full --plan .

# Override model/URL
arckit build --recipe oaa-full --base-url http://localhost:8080 --model Qwen3.6-27B .
```

## O-AA vs TOGAF ADM

| Dimension | `arckit-togaf-adm` | `arckit-oaa` |
|-----------|--------------------|-------------|
| Standard | TOGAF ADM (traditional) | O-AA C208 (agile) |
| Commands | 9 (Preliminary → Phase H + Repository) | 5 (ADM Lite, Product, Strategy, Security, Governance) |
| Cadence | Quarterly architecture boards | 2–4 week sprint windows |
| Artefacts | 200-page deliverables | 1–2 page canvases, max 2/sprint |
| Delivery | Stage-gate (Preliminary → A → H) | Backlog-driven, iterative |
| Organisation | Enterprise-wide, component-focused | Product-centric, cross-functional teams |
| Security | Dedicated phase/gate | Backlog item per sprint |
| Governance | Formal architecture board | Sprint review panels, lightweight evidence |
| When to pick | Full regulatory audit, 50+ stakeholder gates | Hard deadline <8 weeks, agile culture |

**They are complementary** — not competitors. Use `togaf-adm` for enterprise baselines, then `oaa` to execute capabilities at sprint velocity.

## Data

This overlay adds commands, templates and reference material only. It sends no data of its own, and it has no hooks and no MCP servers. Its commands run in Claude alongside the `arckit` core plugin, whose README lists what that plugin sends and when. Privacy policy: <https://arckit.org/privacy.html>.
